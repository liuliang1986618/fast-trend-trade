# 提交规范（commit message convention）

> **立规时间**：2026-09-19
> **触发**：用户反馈「提交的 log 写的不够详细和精准，log 中要比较详细的体现本次的重要内容」
> **适用范围**：本仓库全部 commit（含 AI 代写）

---

## 一、格式

```
<type>(<scope>): <subject，≤50 字，说清"做了什么 + 为什么">

【背景】
【改动】
【成果】
【验证】
【影响与风险】
【遗留】
```

**type** 取值：`feat` 新功能 ｜ `fix` 修缺陷 ｜ `docs` 文档 ｜ `refactor` 重构
｜ `chore` 杂项/工具 ｜ `data` 数据口径/台账 ｜ `report` 日报呈现 ｜ `config` 策略参数

**scope**：模块名（如 `species` 物种分诊 / `emotion` 情绪池 / `sector` 板块数据 / `report` 日报）

---

## 二、要素要求

| 要素 | 必须性 | 内容要求 |
|---|---|---|
| **subject** | ✅ | 一句话说清"做了什么 + 为什么"。**禁用**"优化""调整""完善"等空词 |
| **【背景】** | ✅ | 触发本次改动的**具体原因**：问题现象 / 新发现 / 用户请求。含可核查的细节（日期、命令、数值） |
| **【改动】** | ✅ | **逐个文件**列出 + 关键实现要点（阈值、算法、参数）。读者不看 diff 也能明白动了什么 |
| **【成果】** | ✅ | **量化**（数字 + 口径 + 时点）。确实无量化时，明确写"本次无量化产出" |
| **【验证】** | ⚠️ 复杂改动必写 | 怎么确认生效（执行的命令、对比基准、观测结果） |
| **【影响与风险】** | ⚠️ 影响下游时必写 | 对既有流程/数据/上游依赖的影响；已知风险与未验证假设 |
| **【遗留】** | ✅ | 未完成项、已知缺口、下一步动作（无则写"无"） |

## 三、正反例对照（取自本仓库真实历史）

### ❌ 改进前 —— `6c3b02f`（2026-09-18）

```
docs(sector): 修正 3 条过时记录 + 新增「CLI vs MCP 通道」章节

【改判】09-14 记录的「实测不生效」三条，2026-09-18 复测均已可用：
  1. filter --universe <板块码>：生效（40 板块 2934 只，条数与板块家数吻合）
  2. sector_flow_rank：CLI `westock sector ranking` 原生可用（124 板块含资金/上涨家数/龙头）
  3. sector_of：CLI `westock sector constituent` 原生可用（一次拿全成分）
  → 更优替代已写入文档，日常自动化可不再依赖 MCP

【新增第七节】CLI vs MCP 通道对照表（9 类数据的 CLI 命令与状态）+ 单位陷阱说明
（westock quote 的 total_market_cap 单位是「元」，此前按「亿」处理导致两个校验静默失效）。
```

**问题清单**：
1. 没写**为什么现在改**（触发点是"做 P3 时施工发现"，读者无从知晓）
2. 没列**改动文件**（只改了 `docs/sector-data-integration.md` 一个文件，但没写）
3. **影响没说透**——"可不再依赖 MCP"意味着每日自动化可移除一处单点依赖，这是重要结论，却只是一句附注
4. 没写**遗留**（如 ETF 持仓明细仍不可得、`automation-prompts.md` 是否需同步）
5. subject 里"3 条过时记录"过于笼统

### ✅ 改进后（按本规范重写同一改动）

```
docs(sector): 改判 3 条过时接口记录并新增 CLI/MCP 通道对照（P3 施工中发现接口能力已变）

【背景】
  做 P3（数据能力补全）时实测发现：docs/sector-data-integration.md 中
  2026-09-14 记录的「CLI 不生效」结论已经过时——当日复测三条接口均已可用。
  若不改判，后续自动化会继续绕道 MCP（而 MCP 当日正反复限频）。

【改动】
  · docs/sector-data-integration.md
    - 第五节表格 3 行改判：--universe 生效 / sector ranking 可用 / sector constituent 可用
    - 新增第七节「CLI vs MCP 通道」：9 类数据的 CLI 命令对照表 + 单位陷阱说明
      （total_market_cap 单位为「元」，此前按「亿」处理致 2 处校验静默失效）

【成果】
  · 文档层面：3 条错误结论更正，新增 1 个通道对照章节
  · 可直接落地的结论：日常自动化的板块数据可全部改为 CLI，去掉 MCP 单点依赖
  · 交叉验证：CLI 与 MCP 同一数据的数值完全一致（半导体 5 日净流入 2437776.21 万元）

【验证】
  · westock sector ranking --type mainNetInflow5d → 124 板块，半导体 243.78 亿（与 MCP 一致）

【影响与风险】
  · 影响：后续 provider 层实现与每日自动化可去掉 MCP 板块数据依赖

【遗留】
  · ETF/指数持仓明细两条通道均故障（MCP 限频 + CLI 不支持行业主题指数）—— 另见 053c3f3

```

## 四、自查清单（提交前逐条过）

- [ ] subject 能否不看 body 就明白"做了什么"？
- [ ] 【背景】里的触发原因，读者能否复现你的发现路径？
- [ ] 【改动】是否列出了**每一个**被修改的文件？
- [ ] 【成果】的数字是否带**口径和时点**（哪天的数据、什么单位）？
- [ ] 复杂改动是否写了【验证】（凭什么认为改对了）？
- [ ] 是否写了【遗留】（没做完的、有风险的）？
- [ ] 有没有"优化""完善"这类无法验证的空词？

---

## 五、一次提交 vs 多次提交

- **一次提交**：同一主题的改动（改动文件有交集、依赖同一背景）
- **拆分提交**：主题不同（如"修缺陷"与"加功能"）、或影响面差异大（配置 vs 数据）

拆分时，每个 commit 都要独立满足上述要素——**不要因为拆得多就写简略**。
